# 审核方法与输出

用于已有稿件的内容审核或重要材料把关。依据主文件的共用判断原则，按文种、目的和材料选择核查项，不把全部核查项目套到短通知等文件上。

## 1. 明确范围和依据

从用户要求和材料中确认审查对象、读者、目的、版本与范围；指定只审某部分时，在该范围内给出意见。缺少关键信息时，明确采用的假设和待确认项，先完成能判断的部分。

核实范围按实际说明，可组合使用：

- **稿内一致性检查**：依据所提供文稿，检查前后矛盾、遗漏和表达；未验证其陈述是否符合实际。
- **原始资料核对**：将文稿与所提供的文件、清单、记录等逐项核对，标明实际读取的资料及范围。
- **外部来源核验**：需要核对政策、标准或公开案例时，查阅适用的权威原文，记录出处、适用时间和核验结果；未完成的列为待确认。

已读取的原文与未读取的附件、资料目录或转述分开。遇到来源冲突，列出具体差异，核对统计期、范围、状态和版本适用性；不能仅因某份材料更新就认定全部内容更准确，也不能自行平均或拼接成新结论。

简单稿件在审稿意见中直接引用依据即可。来源多、重要数字多或版本冲突较多时，可用简表记录“结论—来源位置—适用时间—口径—冲突/待办”；内部记录不必全部随成稿交付。

## 2. 选择核查重点

### 事实与评价

- 阶段证据支持到哪里，正文就写到哪里。方案中的拟配置清单只能支撑拟配置的内容；合同、到货、安装、投运与验收记录按原文实际内容判断，不由一类记录自动推定其他环节已经完成。
- 核对数据的单位、范围、分母、时间和限定词；“每项上限”与“总额”、“报价”与“批复预算”不可混用。
- “已完成”“全面覆盖”“显著改善”等结论应有对应证据；缺证据时指出待核实之处，不直接认定其虚假，也不擅自补数字。
- 原因、责任、承诺和成效分别检查。事实上的依赖可以写清，但不能把未经核实的责任判断包装成客观结论。

### 结构与必要信息

只看成稿，判断读者能否理解核心结论、依据、当前状态及所需行动；不得依赖对话中未写入的关键前提。

按 [文种结构模板](templates.md) 检查必要信息。需要批准的事项是否可识别，通知要求是否可执行，问题与整改措施是否对应，相关风险是否因压缩而消失。正式行文按已明确适用的制度判断文种边界；内部会议材料按会议目的判断，不强套同一种格式。

### 项目与建设思路

以下仅用于相关项目材料：

| 核查点 | 判断方法 |
| --- | --- |
| 当前状态与范围 | 规划、采购、实施、验收、运行各有依据；现状与拟建设边界清楚 |
| 经费与数量 | 口径、依据、清单对应及合计一致，未把报价或拟定范围写成已批准事项 |
| 架构与清单 | 系统、设备、服务各有用途与归属；术语背后有可理解的业务或组成逻辑 |
| 展开层次 | 足以理解、评估或决定；功能单一的内容不为形式强拆层次 |
| 调研需求 | 问题能转化为设计需要的范围、图示、数量或计划，避免只有笼统的“加强调研” |
| 协调事项 | 已做措施与对方待办均可识别；责任和时限未确认的，保留拟定状态或标明缺口 |
| 对标与模板 | 对标明确标注来源和适用边界；旧项目的专名和数字未混入本项目 |

### 表达与载体

评价的分寸、语气与证据相符；修改套话时保留有效信息。对比目标须有现状依据，不能为了“转变”先贬低现状。通知、说明等可直接写事项，不要求统一的结论摘要或对仗句式。

| 载体 | 内容完成标准 |
| --- | --- |
| 文字正文 | 关键前提、结论、依据和行动可独立理解；必要未知项可见 |
| 一页简报 | 时间范围明确；保留本期变化、重点风险与所需行动，按目的取舍 |
| PPT 提纲 | 每页主题及必要结论清楚；压缩后保留数字口径、状态限定与诉求 |
| 发言稿 | 内容与正文一致，符合指定听众和时长；口语化不扩大成果或承诺 |

只有正文或提纲时，结论限于内容审核。实际文件的版式、文字是否超出版面、格式是否与模板走样、修订记录等，需读取对应文件，用适合的文档或演示工具检查。

## 3. 给出可执行的意见

按影响区分意见，不要求固定数量或评分：

- **必须修改**：已证实的错误、稿内矛盾、已确认的错误引用或口径混用，或影响决策和执行的必要信息缺失。说明可确认的问题及依据，不把缺证据等同于事实虚假。
- **待确认**：原文未提供、材料冲突或依据不足，当前不能确定；说明需要哪项资料或确认。
- **可选优化**：不影响事实和使用的表达、顺序或篇幅建议；不作为通过审核的前提。

仅缺证明资料时，验收、预算批复与覆盖成效等结论均列为“待确认”，先要求补证或核实。需要提交而无法补证时，改为与现有证据相符的限定表述，或保留必要的【待确认】；不能沿用没有证据支撑的确定性说法。能确认稿件将方案当作验收依据、将报价当作预算批复依据，或表述与适用的有效原文矛盾时，才据此列为“必须修改”；事实本身仍按实际核验结果判断。

默认先给简短总体判断，再列具体问题和必要待确认项。可用下表，也可按用户格式写成逐条意见：

| 类型 | 位置与原文 | 依据及影响 | 建议或替换句 |
| --- | --- | --- | --- |
| 〔意见类型〕 | 〔章节/段落/页码及短句〕 | 〔来源位置或稿内矛盾；为何影响使用〕 | 〔可确定的修正，或需核对的资料〕 |

使用能实际定位的章节、段落、页码或原句；不要虚构行号和来源位置。可合并重复问题，重要问题优先。替换句应保留已知事实和限定条件，未知事实使用【待确认】；拟定安排继续用“拟、建议、待审定”等表述。

未发现具体问题时直接说明结果及核实范围，不为凑数制造意见。未取得原始证据时，不使用“事实全部准确”“已验收合格”等扩大范围的结论。

## 4. 收束审核

用户仅要求审核，交付意见与必要的替换句；用户已要求修改，落实授权范围内可确定的修正，简述关键变化和未解决事项。完成后只复核本次改动是否引入新的状态、数字、遗漏或立场变化，不要求固定审核轮次。
