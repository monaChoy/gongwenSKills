# 文种结构模板库

模板供起草、改稿时选结构，也供审核时判断必要信息。按「读者需要知道什么、决定什么」增删；用户提供的格式模板优先。文中标注的数量（页数、条数）均为默认参考值，不是硬性要求，不作为审稿通过条件。

## 模板一 · 信息化/项目前期建设思路汇报

适用：项目前期向业主或上级讲「怎么建」，争取认同与资源。

默认结构：必要性依据 → 目标体系 → 总体架构 → 清单对应 → 实施与调研需求。

按读者需要，可先用短段说明核心判断、当前阶段与需决定事项，再进入主体；不强制另加摘要。必要性可从业务需求或适用政策立论。

### 1. 政策依据

有与主题直接相关的上级文件时使用：文件全名 + 文号 + 印发时间，拆成 3–4 个发力点，后续章节分别呼应这些发力点。没有直接相关文件就从业务需求立论，不硬挂政策。

发力点写法：动宾短语领起 + 一句具体化。

> 例：加快监测感知体系建设——重点实施安全监测设施的更新改造，构建一体化全要素动态监测感知体系。

### 2. 目标体系

覆盖关键维度即可，不要求固定条数。现状有依据且对比有助理解时，可用「旧方式 → 新方式」表达目标；现状未核实时，直接说明拟建立的机制、范围和目标，不预设现有工作粗放或低效。新方式要写明是拟建设、计划还是目标，不能写成已取得成效。

有可靠来源时可配对标案例：项目名 + 有依据的数据 + 相应成效；案例要明确标注为对标项目，与本项目的事实区分开；不强求每条目标都配案例。

目标表达示意（须按资料改写，不能作为现状或成效依据）：

| 维度 | 句式 |
| --- | --- |
| 感知 | 拟补充〔监测对象〕的监测手段，覆盖范围和运行要求按资料说明 |
| 控制 | 在已有线下办理现状有据时，说明哪些环节拟改为数据传递与线上办理 |
| 决策 | 拟引入〔模型/规则〕辅助〔具体决策事项〕，说明适用条件 |
| 配置 | 以〔已核实的配置问题〕为依据，说明拟采用的分配机制或指标 |
| 业务 | 说明拟贯通的业务环节、共享数据与责任边界 |
| 巡检 | 说明现有巡检方式与拟补充手段，以及各自覆盖范围 |

选用对比句时，先确认旧方式的实际动作及不足，再说明新方式的机制与适用范围；避免只有口号或无依据的褒贬。

> 对标案例模板：据〔来源及位置〕，〔对标项目名〕布设〔N〕路视频监控，用于〔有依据的具体业务〕；其做法仅供本项目〔适用部分〕参考。

### 3. 总体架构

要害是讲清思路，不是罗列目录：先立分层、分组件的总体架构，让清单成为架构的具体内容。架构可参照同类成熟项目的框架，按本项目实际裁剪——分几层、分哪些模块，以项目实际为准。

数字孪生场景的一种参考分法：信息化基础设施 / 平台（数据、模型、知识等组成）/ 业务应用 / 网络安全 / 保障体系。仅在项目实际需要这些能力时参考，不预设行业或全部模块必建。

**细化程度**：展开到读者能理解、评估、决策所需的层次为止——通常每个「模型」说得清包含哪些子模型、每类「数据」说得清包含哪些类别；功能单一、边界清楚的模型，按功能、输入输出或组成说明即可，不必强拆子模型。

### 4. 清单对应

配置或采购清单按各项实际属性，对应到架构的相应层级或保障部分（系统、设备、服务分开），保留原始清单的名称、单位与数量，并注明清单当前是方案、采购安排还是其他状态。摘要可压成一页「拟建设〔系统〕〔N〕套、配置〔设备〕〔M〕台……」，具体状态随资料调整；清单复杂、需要逐项核对时另附明细表，不硬压成一段。

### 5. 实施与调研需求

调研需求要问设计需要回答的问题——拿到答案后能定界、画图、算量。常见六类，按需选用：

| 类别 | 问法要点 | 拿到答案后能做什么 |
| --- | --- | --- |
| 利旧盘点 | 现有设施及运行情况 | 定利旧与新增的边界 |
| 底板范围与精度 | 区域范围（航飞、建模范围），DEM/DOM 精度 | 定数据采集与建模工作量 |
| 建模对象 | 区域内有什么建筑物、机电设备 | 定建模清单 |
| 用户与权限 | 管理方之外还有哪些使用群体（公众？上级单位？） | 定权限体系与多端设计 |
| 建设周期 | 系统工期 | 排实施计划与关键路径 |
| 预算口径 | 见下 | 统一对外口径 |

预算口径按当前实际资料表述，区分估算、概算、报价、批复预算；不预设此前沟通历史或范围变化——没有依据就不写「以前提过」「现在增加了」。

行政协调事项（对接人、时间安排）是否写入取决于文件目的：建设思路中可略；需要对方行动时，必须写进需协调事项（见模板二要点）。

## 模板二 · 项目信息/进展汇报

适用：周期性或节点性的进展同步；读者要掌握状态、风险与需协调事项。

默认结构：核心结论 → 项目概况与当前状态 → 计划与实际（偏差及原因）→ 问题风险及措施 → 下一步安排 → 需协调/决策事项。

要点：

- 进展与偏差写实际口径（完成量、节点对比）；延期写清原因、影响范围与补救措施。
- 依赖与协调如实写：涉及上游依赖时写清两部分——我方已采取的措施，以及需对方在什么时间前完成什么。
- 无政策、无案例也可成文；不为凑结构增添材料。

## 模板三 · 专项工作汇报/总结

默认结构：总体情况 → 重点工作与成效 → 存在问题 → 后续安排。需要读者快速判断时，可在开头概述核心结论。

要点：成效要有可核实的证据（数字、验收结论、评价）；存在问题如实写、不回避，并与后续安排中的整改措施一一对应。

## 模板四 · 请示

默认结构：拟请示事项 → 理由与依据 → 方案、资源及影响 → 拟提请决定的内容。

要点：一文一事；金额、数量、时限给出依据（估算口径注明）；拟提请决定的内容写成可批复的表述。

## 模板五 · 情况说明

默认结构：事项背景 → 已核实事实与时间过程 → 原因及影响 → 已采取措施与后续安排。

要点：事实与时间过程依据已核验资料；原因区分已核实原因与待查证因素。后续安排按计划或建议状态表述，核实方式、责任与时限未明确时标【待确认】。

## 模板六 · 通知

默认结构：事项与对象 → 具体要求 → 责任、时限及办理方式。

要点：每条要求可执行、可检查——谁、在什么时间前、做什么、通过什么方式反馈。

## 模板七 · 报告

适用：以陈述情况、说明工作或反映问题为主要目的的报告材料。

默认结构：报告事项与核心情况 → 事实与工作情况 → 问题及影响 → 已采取措施与下一步安排。

要点：

- 区分已做工作、取得成效和拟开展安排，重要评价附相应依据。
- 用于正式行文时，按已明确适用的制度确认文种与结尾。出现要求批准经费、方案等事项时，先判断是否应调整为请示，或单独形成请示文件；制度不明时标【待确认】，不假定审批规则。
- 内部会议汇报按会议目的组织，需讨论或决定的事项可单列；不因名称中有“报告”就套用正式行文的全部要求。

## 配套载体转换

正文转为一页简报、PPT 提纲或发言稿时，先按读者、篇幅或时长取舍，再核对结论、数字、状态和诉求。详细内容检查参见 [审核方法与输出](review-guide.md) 的“表达与载体”。

- 一页简报注明时间范围，优先保留关键变化、风险与所需行动。
- PPT 提纲按页组织主题与必要结论，给重要数字保留单位、统计期和限定词。
- 发言稿按指定时长组织重点，保留事实依据与行动诉求；需要核对实际时长时结合朗读速度检查，不凭空保证时长。

内容提纲与实际文件制作分别交付；只有取得并检查实际文件后，才对版式、模板和页面完整性作判断。
